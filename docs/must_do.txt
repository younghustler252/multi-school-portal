School Portal Architecture Review & Proposed Direction
Executive Summary

After reviewing the current public schema, tenant schema, notification architecture, and the existing notification implementation, the current foundation is good and does not require a rewrite.

The main recommendation is to evolve the platform toward a configurable multi-tenant SaaS architecture.

The key idea is:

The platform defines what is possible, the subscription plan defines what is available, the school decides how it wants the system configured, roles define who can perform actions, automation rules define when things happen automatically, and background workers execute asynchronous work.

This should apply not only to notifications but also to access control, academic configuration, finance, reporting, school branding, and other operational behavior.

1. Keep Public and Tenant Domains Separate

The current separation between:

PlatformNotification

PlatformNotificationRecipient

and:

SchoolNotification

SchoolNotificationRecipient

should remain.

Platform notifications represent:

Platform → School

Tenant notifications represent:

School → Student / Guardian / Staff

There is no need to merge these simply to have one notification model.

The current separate tenant-schema approach is also useful for data isolation.

2. Notification Architecture

The current School notification implementation already has the right basic entities:

SchoolNotification
SchoolNotificationRecipient


The main change should be how delivery is executed.

Current approach:

Create Notification
    ↓
Create Recipient
    ↓
Immediately create Email/SMS Queue Job


Recommended approach:

Create Notification
    ↓
Create Recipient
    ↓
Recipient status = QUEUED
    ↓
Queue recipientId
    ↓
Worker loads Recipient
    ↓
Resolve current contact information
    ↓
Send through provider
    ↓
Update Recipient status


The database should remain the source of truth for delivery state.

The queue should be treated as the execution mechanism, not the authoritative notification record.

Queue jobs should preferably contain:

recipientId


rather than copying:

email
phone
title
message


into the job payload.

This prevents stale recipient information and makes retry/idempotency easier.

3. Improve SchoolNotificationRecipient

The current recipient model is good but should eventually include more delivery lifecycle information.

Recommended additions:

nextRetryAt
queuedAt
sentAt
failedAt
cancelledAt


Potentially:

providerResponse
idempotencyKey


The recipient should be able to represent:

PENDING
QUEUED
SENT
DELIVERED
READ
FAILED
CANCELLED


with retry information.

The notification itself represents the broadcast/event.

The recipient represents an individual delivery attempt.

4. Use the Queue, Not Database Polling

The ISP implementation has a database-backed dispatcher. That is useful as a conceptual reference for its state machine and retry behavior, but the school system already has a real job queue.

Therefore the school system should use:

Database = source of truth
Queue = execution mechanism
Worker = delivery executor


Do not replace the school's queue with a database polling dispatcher.

Instead, take the strong ideas from the ISP implementation:

explicit delivery states

retry count

retry policy

priority

provider message ID

failure reason

delivery timestamps

idempotency

and combine those with the school's queue architecture.

5. Add a Reliable Queue/Outbox Strategy

There is one important failure scenario:

Create recipient in database
        ↓
Process crashes
        ↓
Queue job is never created


This leaves a recipient permanently stuck.

There should therefore eventually be either:

Preferred

An outbox:

Transaction
 ├── Notification
 ├── Recipient
 └── OutboxEvent
        ↓
Commit
        ↓
Outbox worker
        ↓
Queue

Simpler initial approach

A reconciliation job that periodically finds queued recipients that do not have an active job and re-enqueues them.

The system should never depend on the queue being perfectly synchronized with the database.

6. Move Toward Permission-Based Authorization

The current public User model has:

role


with a fixed enum:

super_admin
school_admin
principal
teacher
bursar
student
guardian


This is acceptable for the first version but should not remain the long-term authorization model.

The school portal should move toward:

Permission
    ↓
Role
    ↓
User/Membership


Example permissions:

students.view
students.create
students.update
students.delete

attendance.view
attendance.manage

grades.view
grades.manage
grades.publish

fees.view
fees.create
fees.manage
fees.refund

reports.view
reports.generate
reports.publish

notifications.send
notifications.manage

users.view
users.invite
users.manage

settings.view
settings.manage


Roles then group permissions.

Example:

Teacher
 ├── students.view
 ├── attendance.view
 ├── attendance.manage
 ├── grades.view
 └── grades.manage

Bursar
 ├── students.view
 ├── fees.view
 ├── fees.create
 ├── fees.manage
 └── reports.view

7. Support Custom School Roles

School administrators should be able to create roles such as:

Academic Coordinator
Finance Officer
Receptionist
Head Teacher
Examination Officer
Transport Officer


but they should NOT be able to invent arbitrary permissions.

The platform owns the permission catalogue.

The school can combine the permissions that the platform makes available to schools.

This prevents a school administrator from accidentally creating a role that can perform platform-level or security-sensitive operations.

8. Use Default Roles + Custom Roles

Schools should receive default roles out of the box:

School Admin
Principal
Teacher
Bursar
Student
Guardian


Advanced schools can then:

Clone Teacher
    ↓
Modify permissions
    ↓
Academic Coordinator


This means most schools never need to understand the full permission system.

Only schools with unusual organizational structures need custom roles.

9. Plan Limits Should Control Customization

The subscription plan should control limits such as:

maxStudents
maxStaff
maxCustomRoles
maxNotificationRules
maxAutomationRules


For example:

Starter
    5 custom roles
    5 automation rules

Professional
    20 custom roles
    50 automation rules

Enterprise
    higher/custom limits


The plan should control entitlement.

The role should control authorization.

These are separate concepts.

10. Consider Tenant-Scoped Membership

Instead of having the public User permanently own one role, the architecture should eventually support:

User
  ↓
SchoolMembership
  ↓
Roles


This makes the authorization model cleaner and allows a user to have different responsibilities in different tenant contexts if the product ever needs that.

Because the platform uses separate public and tenant schemas, identity can remain in the public schema while school-specific membership, roles, and permissions can live within the tenant context.

11. Introduce a Proper Configuration Concept

The current SchoolSettings model is already the beginning of this.

The next architectural step is to treat configuration as a first-class part of the product.

Configuration should be organized into areas such as:

School
Academic
Finance
Notifications
Reports
Access
Security
Integrations


Not everything should become one giant JSON settings object.

Core business concepts should remain proper database models.

Configuration should control behavior around those models.

12. Distinguish Settings, Policies and Automation

This distinction is important.

Settings

"What does this school prefer?"

Examples:

timezone
logo
branding
report template
default grading configuration

Policies

"What rules does this school follow?"

Examples:

passing score = 40%

fee grace period = 7 days

allow student login = true

Automation

"What should the system do automatically?"

Examples:

7 days before fee due
→ remind guardian

student marked absent
→ notify guardian

report card published
→ notify guardian

every Monday
→ send parent attendance reminder


These should not all be represented as one generic setting.

13. Notification Rules

Introduce a school-level notification/automation rule concept.

Examples:

Weekly Parent Reminder
Every Monday at 8:00 AM
Target: All Parents
Channels: Email + In-App
Status: Active

Attendance Alert
Trigger: Student marked absent
Target: Guardian
Channels: SMS + In-App
Status: Active

Fee Reminder
Trigger: 7 days before invoice due
Target: Primary Guardian
Channels: Email + SMS
Status: Active

Report Card Notification
Trigger: Report card published
Target: Guardian
Channels: Email + In-App
Status: Active


The school administrator should be able to:

Create
Edit
Enable
Disable
View
View history

14. Configuration Should Be Visible

The administrator should be able to see what is currently configured.

For example:

Notification Automation

ACTIVE

✓ Weekly Parent Reminder
  Every Monday · 8:00 AM
  All Parents
  Email + In-App

✓ Fee Due Reminder
  7 days before due date
  Primary Guardians
  Email + SMS

✓ Attendance Alert
  On student absence
  Guardian
  SMS + In-App


INACTIVE

Report Card Notification
  On publication
  Guardians


The product should not make important behavior invisible.

15. Configuration Should Support Platform Defaults and School Overrides

Because this is a SaaS platform, configuration should eventually support:

Platform Default
        ↓
School Override
        ↓
Effective Value


Example:

Platform default:
Fee reminder = 7 days

School override:
Fee reminder = 5 days

Effective value:
5 days


The UI can show:

5 days

School override
Platform default: 7 days


This gives the platform a sensible default while allowing each school to operate differently.

16. Configuration Changes Must Be Audited

The existing AuditLog model should be used for:

Role created
Role deleted
Role permissions changed

Notification rule created
Notification rule enabled
Notification rule disabled
Notification rule changed

Fee policy changed
Grading configuration changed
School settings changed
Security settings changed


The audit record should capture:

who
what
before
after
when
IP
user agent


This is particularly important for financial, academic and permission changes.

17. Avoid an Overly Generic Automation Engine Initially

Do not immediately build a universal:

IF condition
THEN action


engine for the entire application.

Start with domain-specific rules:

FeeReminderRule
AttendanceNotificationRule
ReportCardNotificationRule


They can share infrastructure underneath.

Once several real use cases prove that the same abstraction is needed, the common automation layer can be extracted.

This will be easier to test, explain and maintain.

18. Review Existing SchoolSettings

The current SchoolSettings model is useful but mixes several concerns:

branding
report cards
principal information
teaching model
student login


The application should conceptually separate:

School Branding
Academic Settings
Report Settings
Notification Settings
Security Settings
Finance Settings


They do not necessarily all need separate database tables immediately, but they should be separate configuration modules.

Also, values such as principalName should preferably be derived from the authoritative Staff/User relationship rather than stored independently if the principal is already represented as a staff member.

Final Architectural Principle

The system should ultimately follow this model:

PLATFORM
"What capabilities exist?"

        ↓

PLAN
"What capabilities does this school have?"

        ↓

SCHOOL CONFIGURATION
"How does this school want them to behave?"

        ↓

ROLE / PERMISSION
"Who is allowed to do what?"

        ↓

AUTOMATION RULE
"When should the system act automatically?"

        ↓

DOMAIN SERVICE
"What business operation should happen?"

        ↓

QUEUE / WORKER
"How should asynchronous work execute?"

        ↓

AUDIT
"What happened, who caused it, and what changed?"


This gives the School Portal a much stronger foundation than hard-coding every school behavior.

The goal is not to make everything configurable for the sake of flexibility. The goal is to make the right things configurable while keeping security, business rules, and tenant boundaries under platform control.
